# Deployment Parameters are plain text; secrets come from the Agent's environment

Narrows [0004](0004-admin-uploaded-deployment-scripts.md).

A Deployment Script version declares Deployment Parameters in a comment block of its own content, and each Deployment gives their values, which the Agent hands the script as `DEPLOY_PARAM_` variables. The values are stored as plain text on the Deployment, returned by every read of it to anyone who may read Deployments (Organization Administrators), shown in its form, and put in the Agent's work item as they are. They are not encrypted, masked or treated as a Secret. A value a script must keep secret, such as a password, an API token or a key for another system, is set in the Agent service's environment on the host, which every script inherits, as it was before parameters.

We chose this because the values parameters exist for are what differs between the places one script puts a Certificate (a site, a port, a pool name), which an Organization Administrator needs to see to check what a script is given, and plain text lets the platform validate them, show them and reuse them on every renewal without a key to manage. Treating them as Secrets would mean encrypted storage, write-only reads, masking in the form and output, and a decision on who may change one they cannot see, for values that are mostly not secret; it would also invite secrets onto the platform that ADR 0002 keeps keys off. The Agent's environment is the alternative for secrets: it never leaves the host, and the platform neither stores nor shows it.

This does not contradict ADR 0004, which accepts that the platform and its Organization Administrators can run any script on an Organization's hosts and therefore read anything those hosts hold. It narrows what can be given per Deployment: values, not secrets.

Consequences: the Deployment Scripts guide (`docs/deployment-scripts.md`) says that values are plain text and that a run's output is stored and read by Organization Administrators, so scripts must not print them. Audit Events name the parameters set or changed, never their values, so the audit trail and the SIEM it is forwarded to do not become a second copy. The declaration's fields leave room for a later `secret` flag; adding one is a new decision, not a change to this one.
