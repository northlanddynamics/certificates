# An ACME CA is referred to by id; the ACME environment is gone

A Managed Certificate's ACME issuer, an ACME Account and a Certificate refer to an ACME CA by its id (`acmeCaId`), where they had an `environment`, `staging` or `production`, which meant Let's Encrypt's staging or production directory. Let's Encrypt Staging and Let's Encrypt Production are the two built-in ACME CAs, with the ids `letsencrypt-staging` and `letsencrypt-production`; an ACME Account is keyed by Organization and ACME CA. A migration maps every stored `staging` and `production` to those ids, and the `environment` columns are renamed, not kept beside. The API carries only `acmeCaId` (the agent contract names no issuer, so it is unchanged): the issuer is `{ "kind": "acme", "acmeCaId": ... }`, a Managed Certificate and a Certificate have `acmeCaId`, registering an account names `acmeCaId`, and the inventory's `environment` filter is the `tag` filter, which matches the ACME CA's Environment Tag.

We chose this because custom ACME CAs, which an Organization adds by directory URL, cannot be told apart by an environment: two of them can both be "production", and one can be neither. An id names the CA itself, and the environment survives only as a tag, a label that changes nothing. Keeping `environment` as an alias would have left two ways to name the same issuer in the API, with one of them unable to name a custom CA, and every client would have had to handle both.

Consequences: this is a breaking change to the API and hard to reverse, since the migration rewrites stored rows. Clients that sent or read `environment` must send and read `acmeCaId` (`letsencrypt-staging` for `staging`, `letsencrypt-production` for `production`). Audit Events written before the change keep `environment` in their detail; later ones carry `acmeCaId`.
