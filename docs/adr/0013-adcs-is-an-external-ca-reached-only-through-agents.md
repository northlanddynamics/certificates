# ADCS is an external CA reached only through Agents

An ADCS CA is an Organization's Active Directory Certificate Services CA, which the platform issues from and revokes at, but never reaches itself. Every operation on it (discovering its templates and chain, submitting a CSR, checking a pending request, revoking) is a work item that an online Agent assigned to it carries out with MS-WCCE, from a domain-joined Windows host, as that Agent's group managed service account (gMSA). The platform holds no AD credential and no ADCS key, and no work item carries a secret. Because each Agent acts as its own gMSA, ADCS's own permissions on its templates decide what can be issued at all; the platform's Approval and an ADCS CA's Permitted Name Rules are the narrower checks it adds, enforced before anything is submitted.

We chose MS-WCCE from a domain-joined Windows Agent over CES/CEP (the certificate enrollment web services) called from the platform. CES/CEP would have needed an AD credential stored as a Secret and CES deployed beside ADCS, and would have exposed ADCS to the platform's network. Through an Agent, ADCS stays inside the Organization's network, reached only outbound by a host the Organization already runs, and assigning several Agents keeps it reachable when one is down: an Agent that cannot reach the CA passes the work to another.

Consequences: an ADCS CA works only while one of its assigned Agents is online, so its operations wait for one and fail after a deadline. Only Windows Agents can be assigned, and an Agent off Windows answers ADCS work items as refused. CES/CEP remains possible later as another transport behind the same Agent seam (the Agent's ADCS client). ADR 0002 and ADR 0007 are unchanged: the platform still holds no private key, and an ADCS-backed Enrollment Profile keeps the SCEP RA key exception, with only its RA certificate's issuer differing.
